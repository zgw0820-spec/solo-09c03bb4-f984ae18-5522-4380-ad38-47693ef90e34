# MIG 切片调整值班台

单卡 MIG 切片的**排班 / 调整控制台**：值班员为待上线服务补两块新切片，系统在
不移动运行中切片、不破坏已接单切片的前提下给出方案，按「一次一批」的方式执行，
并在驱动报错后核对实际布局、只补未完成的改动。

界面：FastAPI + 原生 HTML/JS（无前端构建步骤），单卡模拟器内置于服务进程。
启动：`docker compose up --build`，浏览器打开 <http://localhost:8000>。

---

## 1. 业务规则

| 规则 | 实现位置 |
| --- | --- |
| 单卡最多 8 个槽位；切片占用一个连续区间 | `app/models.py`（`MAX_SLOTS`，`SlotInterval`） |
| 每种规格声明它允许占用的区间集合 | `SpecDef.allowed_intervals`，导入时校验切片是否落在允许区间内 |
| 运行中切片原地保留，不移动、不拆除、不接单 | `planner.compute_plan` 将 running 视为硬障碍 |
| 两块新切片互不重叠 | 规划枚举组合时排除区间重叠 |
| 拆掉的空闲切片数最少 | 规划排序键 `(拆除数, 新切片总槽位, 字典序)` |
| 已接单的空闲切片不可拆 | `planner._removable` 要求 `order_count == 0` |
| 无解时说明原因 | `PlanResult.error/detail`，区分「被运行中切片挡住」「被已接单切片挡住」「两块新切片可用区间两两重叠」等 |
| 每次只处理一批 | `BatchService` 在 `applying/failed` 时拒绝新的规划 |
| 确认时复核布局与接单状态，冲突则退回重算且**不动卡** | `BatchService._confirmation_conflict` |
| 调整期间仅待拆切片暂停接单，其余空闲切片照常接单 | `confirm()` 只对 `plan.removals` 置 `paused` |
| 驱动可能在改动生效后报错 | `SimDriver.apply` 的 `after_apply` 故障模式（可配置跳过 N 项、连续失败次数） |
| 网页显示实际布局，已建切片留给本批 | `Batch.describe_actual` → `batch.actual` |
| 重试只补未完成的改动，配齐后才交付 | `_remaining_ops` 以实际卡状态计算差集；`_verify_and_deliver` 核对后才把切片转为可接单 |

### 批次状态机

```
planned ──确认（无冲突）──▶ applying ──驱动成功 + 核对通过──▶ delivered
   │                         │
   │ 确认冲突（布局变化 / 待拆切片已接单）
   └────────◀ 重算回 planned │
                             └──驱动报错──▶ failed ──重试（只补未完成）──▶ applying
                                              └── 冲突（待拆切片已接单等）──▶ 保持 failed，提示放弃重规划
```

* `planned`：方案已生成，尚未暂停任何切片。
* `applying`：待拆切片已暂停接单；本批新建切片为 `draft`（状态「本批已建」），
  既不能接单、也不会被下一批当成可拆对象。可通过「确认并暂停（暂缓驱动）」
  停留在该状态测试接单行为，再点「继续调用驱动」。
* `failed`：驱动报错。网页展示**实际布局**与方案差异、哪些切片已建成、哪些待拆仍存在。
* `delivered`：两块新切片均已按方案在位，转为普通空闲切片并开始接单。
* `abandoned`：放弃批次，可回收本批已建切片并解除暂停。

## 2. 运行

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

`docker-compose.yml` 只声明一个服务 `mig-console`，镜像内以 uvicorn 启动，
自带 `/api/state` 健康检查。

### 本地开发

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
pytest -q
```

## 3. 页面与接口

页面分四块：

1. **实际布局**：8 个槽位的色块 + 切片表（规格、区间、状态、是否可接单、订单数）。
   方案中的新切片以紫色虚线框预览，待拆切片以红色虚线框标记。
2. **填写两块新切片并规划**：选择规格、生成方案；有解展示新建/拆除清单，
   无解展示原因与建议。
3. **批次执行与核对**：当前批次状态、计划位置、实际已建/未建成、待拆是否仍存在、
   自由槽位、是否与方案一致；操作按钮随状态变化（确认 / 继续驱动 / 重试 / 放弃）；
   下方是批次事件日志。
4. **模拟器控制**：外部派单（可强制忽略暂停标记，用于测试冲突路径）、外部新增/移除
   空闲切片、驱动故障注入（after_apply / before_apply、跳过 N 项、连续失败次数）、
   JSON 初始布局导入、网页自测。

主要接口（均为 JSON）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 当前布局 + 批次 + 默认布局 |
| POST | `/api/layout/import` | 导入槽位数、规格允许区间、现有切片 |
| POST | `/api/layout/reset` | 恢复示例布局 |
| POST | `/api/plan` | `{"new_slices":[{"spec","name"},{"spec","name"}]}`，必须恰好两块 |
| POST | `/api/batch/confirm` | 确认并执行；`?hold=true` 只暂停不调驱动 |
| POST | `/api/batch/apply` | 调整窗口结束后继续调用驱动 |
| POST | `/api/batch/retry` | 失败后只补未完成的改动 |
| POST | `/api/batch/abandon` | 放弃批次，`?rollback_drafts=false` 可保留已建切片 |
| POST | `/api/order` | 外部派单（`slice_id` 可选、`force` 可忽略暂停） |
| POST | `/api/external/add-idle` / `/api/external/remove` | 外部布局变更 |
| POST | `/api/fault` / `/api/fault/clear` | 驱动故障注入 / 清除 |
| POST | `/api/selftest` | 运行内置自测，返回逐项结果 |

## 4. 自测与验证

### 已实现

- 单卡 8 槽位模型、规格允许区间、切片区间占用与重叠校验、JSON 导入校验。
- 规划器：运行中/已接单不可动，枚举两块新切片区间组合，按「拆除数最少」优先；
  无解分类给出原因。
- 批次状态机：规划 → 确认 → 执行 → 核对 → 交付；确认冲突退回重算；失败重试；
  放弃回收；一次一批的互斥。
- 调整窗口：仅待拆切片暂停，其余空闲切片照常接单；本批新建切片为 draft，
  不接单、不被下一批拆除。
- 驱动层：after_apply / before_apply 故障、跳过 N 项、连续 N 次失败；
  报错后按实际卡状态重算剩余操作，配齐并核对通过后才交付。
- 网页：布局色块、方案预览、实际/计划差异核对、批次事件日志、自测面板。

在浏览器端到端测试中实际观察到：

- 示例布局渲染 8 个槽位、4 块切片；方案预览与“待拆”标记正确。
- 规划 → 确认 → 交付后，「与方案一致」为“是”。
- 无解时展示“运行中切片不允许移动”等原因，且「确认方案」不可点击。
- 调整窗口内：仅 1 块切片显示「已暂停」；对其它空闲切片派单成功并提示“订单已派发”；
  对待拆切片派单被拒，提示“待拆切片已暂停接单”；点「继续调用驱动」后交付。
- 注入 before_apply 故障：批次显示「执行失败」，点「重试」后交付。
- 规划后从外部移除切片再确认：批次退回「方案待确认」，事件日志出现 `CONFLICT` 与
  `REPLANNED`。
- 导入 `slot_count: 9` 被拒绝并显示校验错误。

说明：截图环境下无 CJK 字体，中文在截图中显示为方框，属环境渲染问题；浏览器断言
均基于 DOM 文本，不受影响。

### 未能在本环境验证

- **Docker Compose 实际启动**：本环境未安装 Docker，也没有可用的容器运行时，因此
  `docker compose up --build` 未实际执行；`docker-compose.yml` 仅做了 YAML 结构校验，
  `Dockerfile` 的构建与健康检查未跑过。请在具备 Docker 的机器上执行一次。


已覆盖的关键断言：

- 调整窗口内：非待拆空闲切片派单成功；待拆切片返回「已暂停接单」。
- 确认冲突：规划后外部移除/新增切片，确认时批次回到 `planned`，**未调用驱动**，
  卡上只保留外部改动。
- 待拆切片在确认前接单：退回重算，且新方案不再拆除该切片。
- 驱动 after_apply 报错：批次 `failed`，实际已建切片在网页可见，未建成的仍缺失。
- 重试：已生效的创建/拆除不重复执行（`applied_ops` 去重断言），配齐两块后 `delivered`，
  交付后新切片可接单。
- 无解：返回原因、不可确认、卡布局不变。
- 最少拆除：在可行方案中选择拆除数最小者，且两块新切片不重叠、运行中切片原地未动。

### 待完成 / 已知限制

- **驱动为模拟器**：`SimDriver` 直接修改内存模型；接入真实 NVML / nvidia-smi 的
  驱动适配、真实 MIG 实例的创建/销毁时序与幂等键尚未实现。
- **状态仅存内存**：服务重启后布局与批次丢失；持久化（SQLite/Redis）与多副本一致性
  未做。
- **单卡、单批次串行**：未实现多卡、排队、并发批次；也未做用户/权限与审计留痕。
- **“待拆切片已接单”依赖外部尊重暂停标记**：模拟器允许 `force` 派单来复现该冲突；
  生产环境需要与控制面约定暂停语义或使用排他锁。
- **页面无浏览器自动化回归的 CI 接线**：`tests/e2e.js` 已在本地用 Playwright +
  Chrome headless shell 跑通，但尚未接入 CI，也未把浏览器装进应用镜像。
- 前端为单页原生 JS，未做无障碍与移动端深度适配（仅基础响应式）。
- 未实现的分支：调整窗口内若外部**强制**给待拆切片派单，驱动前会再次校验并让批次进入
  `failed`（已有单测覆盖），但网页上尚无“就地改选其它切片继续”的引导流程，需放弃后重规划。
